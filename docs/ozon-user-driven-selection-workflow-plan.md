# 用户驱动的选品、过程可视化与可售控制功能规划

> 日期：2026-11-13  
> 状态：功能规划，未实施  
> 范围：选品计划 → 用户启动 → 过程可视化 → 原有生图/图审 → 上架时可选库存与 on_sale  
> 本文中的 `[user-decided]` 已由用户确认；`[planned]` 为规划建议，实施时不得当作既有事实。

---

## 1. 背景与问题

当前应用的用户感知主要集中在图审，选品为何启动、按什么逻辑运行、正在处理什么、发现了哪些热卖商品，以及这些商品对应哪些 1688 货源，都缺少连续可见性。

这造成三个问题：

1. 用户无法在执行前判断选品方向、数据预算和停止条件是否符合预期；
2. 运行中只能等待最终结果，无法发现错误方向、异常消耗或错误货源映射；
3. import 成功后，库存和是否立即销售缺少显式用户意图，容易把“商品卡已创建”误当成“商品已可售”。

本规划将产品入口从“系统默认开跑”改为“用户确认计划并主动启动”，并将选品过程变成可观察、可解释、可恢复的任务。

---

## 2. 已确认的产品决策

1. `[user-decided]` 默认进入选品计划页，不自动执行选品，不在启动前消耗 Nexscope 积分。
2. `[user-decided]` 用户可调整类目范围、排除方向、候选数量、数据预算和种子词，再点击开始。
3. `[user-decided]` 运行过程展示真实阶段、数量、当前对象、成功/失败数、热卖商品和对应 1688 货源；无法计算总量时不展示伪百分比。
4. `[user-decided]` 设置库存与上架后立即销售是两个独立选项，均默认关闭；on_sale 必须满足内容审核通过且库存大于 0。
5. `[user-decided]` 本切片基于现有 Web 应用完成，不等待 PostgreSQL、LangMem、完整 Harness 或 ComfyUI。
6. `[user-decided]` 选品完成后复用原有生图与图审逻辑，不在本次重做图审。

## 3. 目标与非目标

### 3.1 目标

- 用户在花钱查询前理解并批准选品逻辑。
- 选品只能由用户显式触发。
- 用户能随时回答：当前在哪一步、为何停住、已经发现什么、花费多少、下一步是什么。
- 热卖商品与 1688 货源之间是可追溯的映射，不是两个无关列表。
- 未通过趋势/经济检查的商品不得被包装成合格候选进入付费媒体生成。
- 用户明确选择是否设置库存以及是否进入 on_sale。
- 选品结束后无缝进入现有生图和图审流程。

### 3.2 非目标

- 不迁移 PostgreSQL，不引入 LangMem、LangGraph、Temporal 或 ComfyUI。
- 不重做图审、Prompt 管理、长期记忆或通用 BI 看板。
- 不做多用户、角色权限、公开 SaaS 或移动优先界面。
- 不让 LLM 直接决定数值阈值、利润、合规或真实上架。
- 不在本切片实现自动采购、自动履约、售后或自动补货。

## 4. 核心用户旅程

```text
打开应用
  ↓
选品计划（未执行）
  ├─ 查看 AI 推荐方向、依据和不确定性
  ├─ 查看数据查询逻辑、预算和停止条件
  └─ 修改结构化计划字段
  ↓
用户点击「开始选品」
  ↓
运行详情页
  ├─ 阶段进度与实时日志
  ├─ 热词与热卖商品
  ├─ 每个商品对应的 1688 top3–5 货源
  ├─ 趋势/经济检查结果
  └─ 失败、费用与等待人工状态
  ↓
合格候选进入现有生图流程
  ↓
原有图审与上架编辑
  ↓
上架操作确认
  ├─ 设置库存：默认否
  └─ 审核通过后进入 on_sale：默认否
  ↓
listed / on_sale / 需要人工处理
```

## 5. 功能规划

### F1. 选品计划页

#### 页面内容

1. **推荐方向**：场景、季节/节日、目标人群、类目和推荐理由。
2. **不确定性说明**：推荐只是待验证假设，不代表已有市场需求数据。
3. **可编辑字段**：
   - 计划名称；
   - 种子词/方向；
   - 包含与排除类目；
   - 目标候选数量；
   - Nexscope 查询预算；
   - 本次允许的最大付费媒体候选数；
   - 停止条件。
4. **数据获取逻辑**：每个数据源用于验证什么、预计查询次数、哪些数据当前不可用。
5. **执行前摘要**：方向、范围、预算、预计产出和开始按钮。

#### 页面状态

- 正在生成计划；
- 计划生成失败，可重试；
- 计划草稿，可编辑；
- 计划就绪，可启动；
- 已有运行任务，可继续查看，不重复启动。

#### 启动约束

- 只有用户点击「开始选品」才能创建运行任务。
- 启动时再次校验预算、数量和必填范围。
- 同一份计划重复点击只能产生一个活动运行。
- 页面刷新或应用重启不得自动启动未确认计划。

### F2. 运行阶段与真实进度

#### 阶段定义

| 阶段 | 用户看到的内容 | 完成依据 |
|---|---|---|
| 计划确认 | 已批准的计划快照 | 用户启动动作已记录 |
| 热词获取 | 当前数据源、已查询/总查询、积分消耗 | 查询任务结束或触发停止条件 |
| 候选商品 | 当前热词、已发现/通过/淘汰数量 | 确定性漏斗完成 |
| 1688 找货 | 当前商品、已找货/无货源/待确认数量 | 每个候选均有明确结果 |
| 趋势检查 | 当前词、正常/告警/查询失败数量 | 每个候选有真实检查结论 |
| 经济检查 | 当前商品、通过/判负/缺参数数量 | 定价快照与硬闸结论存在 |
| 交付生图 | 已进入现有流程的商品数 | 候选交接记录完成 |

#### 进度规则

- 总量已知时显示 `已完成 / 总数` 与百分比。
- 总量未知时只显示阶段、当前对象和已完成数量。
- 不用定时动画伪造进度。
- 失败、等待人工、已暂停和已完成必须有不同视觉状态。
- 每个阶段都可展开查看输入、输出摘要和失败原因。

### F3. 热卖商品与热词展示

每张候选卡至少展示：

- 商品标题、图片、来源链接；
- 命中热词与推荐方向；
- 类目及类目确认状态；
- 已获取的需求、竞争、价格等指标；
- 各指标来源与采集时间；
- 入选/淘汰原因；
- 当前所在阶段。

缺失数据展示「未获取」，估算数据明确标为「估算」，不得补造精确值。

### F4. 商品与 1688 货源映射

热卖商品卡内直接展示其 top3–5 货源，而不是另设孤立货源列表。

每个货源展示：

- 商品图、标题和 1688 链接；
- 价格、销量、起订量（有数据时）；
- 相似度/同一性检查状态；
- 发货时效/现货信息（数据源支持时，否则显示未获取）；
- 当前是否被人工选为采购货源。

低置信同一性、无货源和查询失败必须可区分。最终货源选择仍由人工确认，不自动把 top1 当成用户已选。

### F5. 失败、暂停与恢复 `[planned]`

- 用户可停止尚未开始的后续查询；已发出的付费请求如实标记为不可撤回。
- 失败任务展示错误、已消耗费用和是否可安全重试。
- 重试使用原运行记录，不重复创建候选或重复执行已完成阶段。
- 页面刷新只恢复展示，不重新触发任务。
- 无货源、趋势告警、缺定价参数可进入等待人工，不被算作成功完成。

### F6. 与原有生图/图审交接

- 只有通过真实趋势处置与经济硬闸的候选才能进入生图。
- 交接后展示「已进入生图」链接，点击可进入现有商品 Trace 或图审页面。
- 原图审三动作、打回原因和编辑流程保持不变。
- 选品运行页不重复提供图审操作。

### F7. 库存与 on_sale 选项

上架确认区增加两个独立控件：

#### A. 设置库存

- 默认关闭。
- 开启后才启用库存数量输入。
- 数量必须为正整数，并受本次业务上限约束。
- 关闭时不得调用库存设置接口。

#### B. 内容审核通过后进入 on_sale

- 默认关闭。
- 只有勾选设置库存且数量大于 0 时才可选择。
- 该选项表达用户意图，不得绕过内容审核。
- import 成功但 moderation 未完成时，只记录「等待审核」，不得提前标记 on_sale。
- moderation 驳回或库存设置失败时进入人工处理，不得自动反复重试外部写。

#### 结果状态

| 用户选择与实际条件 | 结果 |
|---|---|
| 不设置库存、不进入 on_sale | 商品卡创建/更新后保持 `listed` |
| 设置库存、不进入 on_sale | 库存成功后保持 `listed`，展示已有库存 |
| 设置库存并选择 on_sale，审核通过 | 库存成功后进入 `on_sale` |
| 选择 on_sale 但审核未通过 | 保持非 on_sale，进入人工处理 |

每次执行前展示本次将发生的真实外部写操作；不得把上次选择记忆为默认开启。

## 6. 信息架构

```text
选品
  ├─ 计划列表/新建计划
  ├─ 计划详情（编辑与启动）
  └─ 运行详情（进度、候选、货源、费用、失败）

审核
  └─ 原有图审与上架编辑

流水线
  ├─ 状态看板
  ├─ 已过审/待上架
  └─ 上架失败/待人工
```

运行详情建议使用桌面双栏：左侧为阶段与运行状态，右侧为当前阶段详情和候选卡。窄屏下转为单列，但本切片不做移动优先设计。

## 7. 验收契约

### 7.1 计划与启动

- 启动应用后没有任何选品 API 调用或积分消耗。
- 用户能修改全部已确认的结构化计划字段。
- 只有点击开始后才创建运行。
- 连续双击开始只产生一个活动运行。
- 计划快照在启动后固定，后续编辑不影响已运行实例。

### 7.2 进度与映射

- 每个阶段都有未开始/进行中/成功/失败/等待人工的明确状态。
- 总量未知时不显示百分比。
- 页面刷新不重复执行。
- 每个热卖商品可看到入选依据及数据来源。
- 每个商品可看到其对应 top3–5 1688 货源或明确无货源原因。
- 费用与失败数量随真实执行记录更新。

### 7.3 业务闸门与交接

- 趋势/经济未执行时不得显示已通过。
- 经济判负或缺必要参数的商品不得进入付费生图。
- 合格候选能够进入现有图审，且原流程回归通过。

### 7.4 库存与 on_sale

- 两个选项默认均关闭。
- 不设置库存时零库存 API 写调用。
- 库存为空、非整数或小于 1 时不能提交。
- 未设置库存时不能选择 on_sale。
- moderation 未通过时不能进入 on_sale。
- import 成功但用户未选 on_sale 时保持 listed。
- 所有外部写失败均有可见错误和人工入口。

### 7.5 UI 验收场景

需要留存以下状态的浏览器截图并进行人工核对：

1. 计划草稿；
2. 计划就绪；
3. 运行中且总量未知；
4. 运行中且有候选/货源；
5. 等待人工；
6. 部分失败；
7. 完成并交接生图；
8. 上架选项默认关闭；
9. 库存开启但 on_sale 关闭；
10. moderation 未通过时禁止 on_sale。

## 9. 建议测试边界

以下是规划中的公共测试 Seams，实施前仍需按 TDD 约定确认：

1. **计划 HTTP/API 边界**：验证编辑、启动、重复启动和零意外消耗；不覆盖模型推荐质量。
2. **运行进度查询边界**：验证真实阶段、刷新恢复、失败与重试；不覆盖具体页面像素。
3. **候选交接边界**：验证只有合格候选进入生图；不覆盖生图质量。
4. **上架执行边界**：验证库存/on_sale 选项组合与 moderation 前置条件；外部 API 全部 Mock。
5. **浏览器 UI 验收**：验证用户能否理解进度、映射、风险和恢复动作；不使用 UI 截图替代业务逻辑测试。

## 10. 实施顺序与依赖

```text
Slice A → Slice B → Slice C → Slice D → Slice E → Slice F
```

- A/B 先证明“用户启动 + 真实进度”的最小闭环。
- C 只展示已有真实数据，不为界面增加虚构字段。
- D 必须先保证趋势/经济状态真实，再交接生图。
- E 可在 D 后独立实施，但真实 on_sale 验证需用户另行授权外部写操作。
- 每片完成即跑测试与对应 UI 验收，不一次性水平铺开全部任务。

## 11. 风险与待验证项

1. 现有选品与找货入口是否能安全拆成逐阶段执行，需要实施前做代码级 Spike。
2. Nexscope 与 1688 可用字段决定页面能展示什么；未获取字段不得编造。
3. 趋势/经济闸目前在评审中被确认存在缺口，本规划要求其先变真，不能只做进度外观。
4. `on_sale` 是新业务结果语义，实施前需核对现有状态机迁移和 Ozon 实际行为。
5. 真实库存和 on_sale 测试属于外部写操作，需另行获得用户授权；默认仅以 dry-run/Mock 验收。
6. 本规划不承诺 AI 推荐方向的商业准确性，计划批准只代表用户同意验证该假设。

## 12. 完成定义（DoD）

本功能切片只有在以下条件全部满足后才算完成：

- 用户完全控制选品启动与数据预算；
- 运行阶段、候选、货源、失败和费用全程可见；
- 不存在虚假进度、虚假利润或虚假闸门状态；
- 合格候选可进入原有图审；
- 库存和 on_sale 默认关闭且执行边界经过测试；
- 项目测试全绿，UI 十项状态截图验收通过；
- 未引入 PG/LangMem/ComfyUI 等范围外改造。
