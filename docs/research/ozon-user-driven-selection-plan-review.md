# 用户驱动选品功能规划审核：架构、实现与成本

> 日期：2026-11-13  
> 审核对象：`docs/ozon-user-driven-selection-workflow-plan.md`  
> 方式：主 Agent 直接审核，未使用子 Agent；基于当前源码，不假设 Harness 已存在。  
> 结论：**方向合理，需修改后实施。主要工作量在 Run 级执行与恢复、现有 Worker 改造和真实业务闸门，不在进度条本身。**

---

## 1. 审核结论

### 可以保留

- 用户确认计划后再启动；
- 真实阶段与数量，而非伪百分比；
- 热卖商品与 1688 货源的可追溯展示；
- 原图审复用；
- 库存和 on_sale 默认关闭；
- 不引入 PG、LangMem、完整 Harness 或 ComfyUI。

### 必须修正

1. 增加 Run 级模型，不能把一次选品运行直接等同于商品状态机。
2. 现有“最新 artifacts 文件”模式必须改为 Run 隔离，否则无法可靠恢复和查看历史。
3. 后台执行不能放在 HTTP 请求线程；也不建议用不可恢复的进程内后台线程。
4. 计划生成本身也应由用户点击触发，避免打开页面就产生模型调用。
5. Nexscope 预算必须同时受计划预算和当日剩余额度约束，并在每次付费调用前检查。
6. 选品词不能在候选导出时永久消费；取消/失败需要释放或保留明确状态。
7. on_sale 是实现后的业务结果，不应设计成一个可绕过 moderation/库存的独立 API 动作。
8. Slice A/B 的真实付费执行必须在 D 的真实闸门前保持禁用或使用 Mock，不能先做出“可启动但会带病进入生图”的版本。

## 2. 架构审核

### A1【Critical】Run 与 Product 是两种不同状态

**证据**：当前 `products.state` 表达单商品生命周期（`pipeline.py:25-44`）；规划新增的是一次选品批次，包含多个词、多个 Ozon 商品和多组货源。

若混用，会出现：

- 一个 Run 部分成功时无法表达；
- 同一商品属于不同 Run 时历史和费用无法区分；
- 商品从 imaging 打回会错误影响整个 Run 状态。

**最小修正**：新增独立 `selection_plans / selection_runs / selection_events`，候选详情可用 Run 内 artifacts 保存；只有进入现有商品链路时才写 `products`。

### A2【Critical】“最新文件”无法支撑多次运行

**证据**：

- `select_products.py` 输出 `candidates-YYYYMMDD.json` 与 `image-search-tasks-YYYYMMDD.json`；
- `sourcing_agent.py:297-336` 读取最新 image-search tasks；
- `sync_to_db.py:47-185` 读取最新 candidates/sourcing/spec/gen artifacts。

同日多次运行会覆盖或串读；历史 Run 也无法还原自己的输入与输出。

**最小修正**：每次运行使用 `data/runs/<run_id>/` 隔离 candidates、sourcing、events 和交接清单。现有全局日期文件只作为旧路径兼容，不再成为新流程的事实源。

### A3【High】执行模块需要独立进程，不应由 Web 请求承载

**证据**：当前 `review_server.py` 是 `ThreadingHTTPServer`；现有选品/找货都是长任务 CLI。规划要求页面刷新恢复、失败重试和运行中查看。

**取舍**：

| 方式 | 评价 |
|---|---|
| HTTP 请求内同步执行 | 排除：浏览器超时、无法持续查看 |
| Web 进程内后台线程 | 最小但恢复差，进程退出即丢失执行状态 |
| 每 Run 一个独立 Python 子进程 | **推荐**：复用现有代码、隔离崩溃、Web 只负责启动与查询 |
| 完整 Harness/Celery/PG | 本切片排除，超出当前规模 |

建议使用 `selection_runner.py` 作为独立进程入口。Web 不解析 stdout 猜进度，Runner 直接写结构化 Run 事件。

### A4【High】现有 Worker 接口需要返回值与事件，而非只写文件

**证据**：`select_products.main()` 直接消费词并写文件；`sourcing_agent.main()` 自行读取最新任务文件；`sync_to_db.sync()` 自行发现 artifacts 并推进状态。

**最小修正**：保留 CLI，同时抽出少量可调用接口：

- 输入显式接收计划快照/Run 目录；
- 输出返回结构化结果；
- 每阶段结束写 Run 事件；
- 不在 Worker 内自行决定全局“最新文件”。

不需要为每个小函数建立 Adapter 层；Seam 应位于“执行一次选品 Run”的模块接口。

### A5【High】V1 应限制一个活动选品 Run

规划只约束“同一计划不重复启动”，但 Nexscope 当前预算是“检查→调用→记账”分步执行（`nexscope_client.py:38-57`）。多个活动 Run 可能同时通过预算检查。

**最小修正**：V1 全局只允许一个 running 选品 Run。该限制同时降低 SQLite 写并发、费用竞态和 UI 复杂度。未来确有并行需求再引入完整队列。

### A6【High】当前状态推进与真实闸门冲突

**证据**：`sync_to_db.py` 会在 trend/econ 未实现时推进 checked/profitable。

新 UI 若只把这些状态展示出来，会把假进度产品化。Slice D 不是普通接线任务，而是整个流程能否真实交付的前置条件。

### A7【Medium】计划生成与计划执行是两个动作

规划要求打开应用不消耗 Nexscope，但“AI 推荐方向”仍可能产生模型费用。

**最小修正**：默认页只显示空计划或已有草稿；用户点击「生成推荐方向」才调用模型，点击「开始选品」才执行市场数据查询。两种动作分别展示成本性质。

### A8【Medium】on_sale 应是派生结果

当前 realFBS 可售依赖价格、moderation 与库存，而不是任意独立开关。规划中的选项应表示“满足条件后允许进入可售”，实际状态由真实返回结果驱动。

## 3. 修订后的最小架构

```text
review_server
  ├─ 计划编辑 / 生成推荐方向（用户动作）
  ├─ 启动 / 停止 / 重试（用户动作）
  └─ 查询 Run 快照与事件
             │ subprocess，不在请求线程执行
             v
selection_runner（单活动 Run）
  ├─ 校验计划、费用预检
  ├─ 热词与候选
  ├─ 1688 找货
  ├─ 趋势/经济真实闸门
  └─ 交接现有商品/生图流程
             │
             v
SQLite
  ├─ selection_plans：可编辑计划
  ├─ selection_runs：固定计划快照、当前阶段、状态、费用、取消标记
  ├─ selection_events：阶段/候选/错误/费用事件
  └─ 现有 products/events/reviews/keywords/credit_log

文件系统
  └─ data/runs/<run_id>/：候选、货源、交接等 artifacts
```

### 最小模块接口

对 UI 只暴露四个概念操作即可：

- 保存计划草稿；
- 启动计划；
- 读取 Run 快照；
- 请求停止/人工重试。

表结构、子进程、阶段事件和 Worker 细节应隐藏在模块实现内，避免 UI 直接理解所有内部表和脚本。

## 4. 现有代码改造面

| 现有模块 | 必须改动 | 不应改动 |
|---|---|---|
| `review_server.py` | 新计划/运行页面、启动与查询、上架选项 | 原图审决策逻辑 |
| `select_products.py` | 接收 Run 上下文、输出到 Run 目录、词预留语义 | 确定性漏斗规则本身 |
| `sourcing_agent.py` | 接收指定 Run 的图搜任务、写结构化结果 | Ocean 搜索与同一性算法 |
| `trend_check.py` | 修一词一查、支持预上架候选 | 告警由人工处置的 V1 边界 |
| `pricing.py` / 编辑器 | 生成可审计经济快照 | 确定性定价公式 |
| `sync_to_db.py` | 新流程不再读取全局最新文件或跳过闸门 | 旧数据兼容与去重原则 |
| `listing_worker.py` | 接收库存/on_sale 意图，补 moderation 与库存结果 | offer_id 幂等与 import 必填校验 |
| `pipeline.py` | Run 表迁移、必要的状态扩展、并发安全 | 已合法的商品状态约束 |

### 当前“自动开跑”事实需要单独定位

`review_server.py:834-842` 当前 `/` 只重定向 `/board`，该文件没有启动时自动选品逻辑。因此实施任务应写为“将新入口设为计划页并接入用户启动”，不能假设只要在 review_server 删除一段自动启动代码即可；若另有启动脚本，需在 Spike 中定位。

## 5. 成本审核

### 5.1 Nexscope 数据成本

当前本地估算（`nexscope_client.py`）：

- `marketKeywordSearch`：32 积分/次；
- `categoryProducts`：10 积分/次；
- `categorySearch`：32 积分/次；
- 日估算上限：330；
- Nexscope 不回传扣费明细，因此全部是估算，不是账单真值。

若本次新查 `S` 个种子词、对 `T` 个候选词做趋势复查：

```text
本次关键词估算积分 = 32 × (S + T)
当日可用余量 = 330 − spent_today
允许启动条件 = 本次估算积分 ≤ min(用户计划预算, 当日可用余量)
```

示例：5 个新种子词 + 5 个趋势复查词 = 320 估算积分，几乎耗尽当日 330；若完全复用本地词库，则选品本身可为 0，但趋势复查仍有成本。

**规划需要补充**：

- 计划页展示“复用本地词库 / 新增查询”的分别估算；
- 启动前和每次调用前都检查；
- 达到 Run 预算后进入“已停止/待用户增加预算”，不能静默继续；
- UI 同时显示估算成本和账单未对账状态。

### 5.2 生图成本

`image_worker.py:36-37` 当前估算为 `$0.033/图`。标准模板中 6 个 slot 走 AI，slot2 可复用供应商白底图，slot7 条件生成，重试另计。

若 `M` 个商品进入媒体、slot7 生成 `S7` 次、额外重试 `R` 次：

```text
基础生图估算 = $0.033 × (6M + S7 + R)
```

即无 slot7、无重试时，每商品基础估算约 `$0.198`；该数字不包含文案、VL 同一性、尺寸识别、文字质检、OSS 或退货/履约成本。

因此“最大付费媒体候选数”必须作为独立硬上限，并且只能在经济闸通过后扣减额度。

### 5.3 其他模型与服务成本

- 计划推荐、文案、VL 同一性、尺寸/文字检测按实际 token/用量记录，当前审核未核到统一账单单价，不应编造金额。
- 1688 Ocean 的免费额度没有长期保证，不能把“当前未收费”写成永久零成本。
- 成本 UI 应分为：已记录估算、实际用量、待账单对账，不合并成一个伪精确数字。

### 5.4 实现成本方向

| 切片 | 相对实现成本 | 原因 |
|---|---|---|
| A 计划与启动 | 中 | 表单容易，计划快照、幂等启动和模型动作分离不可省 |
| B Run 生命周期 | **高** | 子进程、Run 隔离、事件、刷新恢复、停止与失败语义 |
| C 商品/货源展示 | 中 | 现有 top 数据可复用，但缺字段与映射口径需统一 |
| D 真实闸门与交接 | **高** | 涉及 trend/econ、artifacts、商品状态和现有 sync 改造 |
| E 库存/on_sale | **高** | 外部写、moderation 前置、失败恢复和状态迁移 |
| F 门禁与 UI 验收 | 中 | 公共接口测试、Mock、十类截图与完整回归 |

**结论：这不是一个低成本前端改版。主要成本在 B/D/E。若时间受限，应先交付 A+B 的 Mock/只读 Tracer，再投入真实付费链路。**

## 6. 对原任务拆解的修订建议

1. **A 增加**：计划生成按钮与执行按钮分离；全局单活动 Run；计划预算预检。
2. **B 增加**：独立 Runner 进程、Run 目录、心跳/中断状态；刷新恢复不等于自动重跑付费调用。
3. **B/C 增加**：词从 consumed_at 一次性烧毁改为 Run 预留/最终结果语义；失败与取消不永久烧词。
4. **C 明确**：top3 热卖商品是展示与找货输入，不等于全部进入商品主流程；避免成本扩大。
5. **D 提升为真实交付前置**：经济/趋势未接真前，不允许启用真实媒体交接。
6. **E 明确**：on_sale 是满足 moderation+库存后的结果；无单独绕过开关。
7. **F 增加成本测试**：预算预检、当日余量、Run 上限、媒体数量上限、估算与实际成本口径。

---

## 7. 最终裁决

**方案审核结果：有条件通过。**

产品方向与已确认交互合理，不需要引入更大的框架；但实施前必须把“Run 隔离、独立执行、单活动 Run、成本预检、词预留和真实闸门”补入任务契约。

如果只按原文做页面和进度条，而不改现有 Worker 的文件与状态接口，最终会得到一个观感更好、但仍无法可靠恢复和准确核算成本的演示流程。
